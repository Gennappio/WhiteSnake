I want to think through this new development paradigm with you (mainly for research but also for any kind of automation):
By now codex/claudecode are the entry point for the work of researchers/programmers. But people still tend to wrap their research/automation in traditional software. Imagine I'm doing an annotation task on a database based on data looked up in some papers. With current technology the  natural conclusion for the researcher would be to build a system that has a deterministic part and a part that makes calls to an LLM or Jev for the decision-making and interpretation. At the end of the work the researcher will distribute or give their collaborators a piece of software with a GUI or cli or mcp entry point.
in my view this is an archaic and limited approach.
The truth is that codex is often able to carry out the annotation tasks by writing code on the fly, to make decisions, log, etc... Basically, prompt after prompt, even the collaborator or the boss could get the same result as the researcher's software by using codex. Except they'll have to prompt all over again, make some decisions, analyse some conclusions and annotate them, consume more tokens etc.
If the researcher had somehow kept a memory of the research session with codex so as to keep track of the decisions, of the code generated on the fly for some analyses that only codex used for internal evaluations etc. if for example the whole research process were organised in a thesis-hypothesis-verification-falsification-conclusion database that the boss's codex could access to understand the why behind the decisions taken, THEN you could hand over not a piece of software but an "automation/research process".
For me modern systems shouldn't have cli or mcp access but should always have coding agent access. the way I see it you don't build a system where an orchestrator calls mcp but one where a harness calls other harnesses. Codex is mature enough. At that point every research session automatically has knowledge learned from the researcher who worked on that session and is able to autonomously write more code on the fly wherever there's a "gap".
a sort of fractal system where little by little the gaps can be filled autonomously.
to do something like this, in my opinion, you need to build an observable system in which the child system can tell the parent system what it wants to know and why but above all in which the various attempts get recorded and are quickly and easily accessible and in which procedures can be "promoted" and become a skill/tool/hook.  why write software that can read papers when codex is perfectly capable of it? wherever codex is capable the system will call codex directly. and if the procedure has succeeded, the codex call with the prompt used will become a semi-deterministic procedure.
Get what I mean? what do you think? basically the idea is to replace all the reasoning components that are usually delegated to an llm with coding agents and make it so that all the reasoning considered correct becomes a procedure.

Yes, I follow you. You are proposing that the thing to be handed over is a transferable working capability: an agent, the context it has built, the evidence that justifies its decisions and the procedures it has learned to reuse. Whoever receives this bundle can continue the work, question it and change its premises.
I think this idea is valuable above all in research, where an essential part of the work consists precisely in discovering which procedure makes sense to apply. Turning that research into an application too early can crystallise assumptions that are still provisional and lose much of the know-how developed along the way.
Your strongest observation, in my view, concerns the intellectual work that today gets dispersed between one session and the next: criteria clarified with the researcher, failed attempts, exceptions discovered, small programs written to check a doubt. All of this should become an operational asset of the project.
There are, however, a few distinctions that would make the paradigm much more solid.
The memory must preserve knowledge that is usable and contestable. Saving the whole conversation is useful as an archive, but forcing the collaborator’s Codex to reread it would mean making it repeat part of the interpretive work. I would distinguish at least these levels:
Level	What it preserves
Experience	Attempts, tool calls, executed code, results and errors
Knowledge	Claims, evidence, assumptions, contradictions and open questions
Decisions	Choices adopted, rationales, scope of validity and discarded alternatives
Procedures	Reusable ways of working, with examples and verification criteria


Your thesis–hypothesis–verification–falsification–conclusion database is close to the second level. I would extend it with dependency relations.
In your example: an annotation depends on a passage in the paper, on a certain interpretation and on an inclusion rule decided by the researcher. If the boss changes that rule, the system should identify the annotations to re-examine. This would make the memory useful for correcting the work as well.
I would also keep “the paper states X”, “we observed Y” and “we decided to treat X as Z” separate. They are different objects: mixing them easily turns a project convention into a supposed scientific fact.
For the code used in internal evaluations, yes: scripts, inputs, environment and results should be recorded. The relevant rationales should be made explicit when a decision is taken. An account written at the end can reconstruct a plausible explanation without faithfully representing what determined the choice.
The fractal idea works if every delegation carries an understandable contract with it. A child agent should receive a question, the reason it matters, the evidence already available and the conditions for considering an answer sufficient. It should return a result, evidence, uncertainties and new questions.
For example:
“I need to understand whether these two publications describe the same cohort, because counting them separately could duplicate the observations. I have already compared authors and dates; the comparison of recruitment criteria is still missing.”

This lets the parent evaluate the contribution and the child ask for relevant clarifications. Recursion, on its own, does not provide this quality.
And I would distinguish two structures: delegations can form a tree; knowledge should form a shared graph. Two branches can depend on the same piece of evidence. If each one keeps an isolated copy of its own conclusions, you risk duplications and contradictions that are hard to see.
On “every session has learned”, I would make one clarification: in this architecture the learning resides mainly in the external memory and in the updated procedures. It must be able to survive the closing of the session and a change of model. That is why I would hand over a versioned asset base from which a new session can start again.
On the step from success to semi-deterministic procedure I would be more demanding. A prompt that succeeded once is a good candidate to keep. To promote it you also need conditions of applicability, verified examples, hard cases and a criterion for recognising when it fails. Repeating the same prompt does not guarantee the same decision.
Promotion could then take different forms:
- A skill, when interpreting the case is still necessary.
- An executable tool, when a transformation is sufficiently well defined.
- A hook, when a check has to happen in response to an event.
They are different destinations, not necessarily rungs of a single ladder. And I would also provide for demotion: a previously reliable procedure can become experimental when data, criteria or model change.
Here I see an important design principle: the system should spend reasoning mainly where uncertainty still exists. Reusing a valid result, running already verified code or applying a consolidated procedure should avoid reopening the whole problem every time. The token saving must still be measured: retrieving and interpreting a memory that is too large can cost as much as redoing the work.
On “always coding agent access” I agree, as a possible entry point for the collaborator, but I would not eliminate CLI, API or MCP. They are interfaces the agent itself can use. The decisive architectural choice is how much responsibility you delegate to the component being called: executing an operation, or pursuing a goal, choosing tools and handling exceptions. A harness can offer the latter capability and keep making use of the former.
The basic components already exist: the current documentation describes a Codex harness with code execution, session resumption, delegation to subagents and use of skills; skills can contain instructions, references and scripts. This makes it plausible to build a prototype of your system. It does not yet show that scientific memory, validation and promotion work automatically. Codex harness, skills.
The first experiment I would run would be very concrete: a researcher annotates a small set of papers; a collaborator, in a new session, receives the process and tackles new papers, then changes an annotation criterion. I would measure how many explanations they have to ask the researcher for, which decisions they manage to justify, which results they manage to correct and how much work they repeat.
The decisive point of your proposal is making the judgement developed during the work transferable. The ability to write more code completes the system: it allows it to keep going when the inherited procedures are not enough, leaving in turn evidence and expertise that the next user can reuse.

1. Version of the executed code. Which code produced a result? HEAD alone is not enough if Codex ran a script that was just written and not yet committed: you need to keep its actual snapshot.
2. Version of the knowledge. In which revision was a decision introduced or modified?
3. Version of data and sources. Which PDF, dataset or external response was used? You need content identifiers and, when possible, preserved copies.

I would do it with an execution engine and a learning engine, both on top of Codex. They share the knowledge record, but have different responsibilities:
- The execution engine chooses procedures, starts sessions, manages delegations and verifies results.
- The learning engine analyses recorded experiences, proposes reusable procedures and submits them for evaluation.
The agent can propose a procedure or a delegation. The software manages state transitions, budgets and acceptance conditions. What follows is a proposed architecture, still to be implemented.
Promotion would start from verified work episodes.
An episode would be a unit small enough to be reused: for example, “extract the number of participants per treatment arm”. “Annotating a paper” could contain many episodes.
For each episode I would record question, inputs, attempts, executed code, outputs, checks, the researcher’s corrections and cost. I would also record failures: they are needed to recognise when a procedure is not applicable.
The promotion cycle would be this:
```mermaid
flowchart LR
    E[Recorded experiences] --> C[Candidate procedure]
    C --> V[Separate evaluation]
    V -->|Passed| S[Shadow use]
    V -->|Insufficient| R[Revision or archiving]
    S -->|Confirmed| A[Active version]
    A -->|Errors or changes| Q[Suspended]
    Q --> V
```
I would implement it in five steps.
1. Recognise an opportunity for reuse.
   A process looks for episodes with similar goals, inputs and success criteria. Repetition, high cost or a major correction by the researcher can trigger a candidacy. Three similar cases might be enough to propose a procedure; not to declare it reliable.
2. Extract an explicit procedure.
   A dedicated session reads the episodes and produces a package: instructions, any scripts, conditions of applicability, expected output, checks and cases in which it must abstain. It must generalise the operations while keeping the references to the original experiences.
3. Evaluate it on separate cases.
   I freeze the candidate version and compare it with the active procedure, or with ordinary Codex execution. I use representative cases, hard cases and out-of-scope cases. I measure correctness, serious errors, ability to abstain, cost and time. The cases used to build it are not enough as an evaluation.
4. Use it in shadow mode at first.
   The candidate produces results without directly updating the final database. I compare them with verified results. For operations with external effects, this phase must work on copies or simulations.
5. Activate a specific version.
   The software applies a promotion policy defined before the evaluation. If it passes, it updates the registry of active procedures. It keeps the previous version and the rationale for the promotion.
The policy would not be “the evaluator agent says it’s fine”. It would include quality thresholds, case coverage, unacceptable errors and cost-effectiveness. An LLM judge can contribute, but two agents that agree do not constitute an independent verification. Where reference answers or reliable checks are missing, the procedure can remain experimental.
This approach also follows the principle of evaluations that are specific to the task and repeated when the system changes. Documentation on evaluations.
The promoted procedure would have a versioned contract.
A manifest might look like this; the fields are part of the system I would build:
id: extract_trial_arm_sizes
version: 3

implementation: skill
entrypoint: SKILL.md

input_schema: schemas/paper.json
output_schema: schemas/arm_sizes.json

applicability:
  - paper with extractable text
  - identifiable participant table

abstain_when:
  - unresolved incompatible denominators
  - only an illegible figure available

source_episodes:
  - episode_018
  - episode_041

dependencies:
  annotation_policy: "2"
  table_extractor: "1"

evaluation_report: eval_027
The qualification would cover procedure + model/harness + dependencies + scope of use. Changing a relevant component requires a new verification.
I would also separate two decisions:
- How much operational trust do we have in the procedure?
- How is it best executed: skill, script or a combination?
A skill can be very reliable while still retaining an interpretive part. Converting it into code is a further optimisation, to be verified through comparisons on the same cases.
A procedure can also learn to delegate. For example: “if the denominator cannot be resolved from the main text, open a check on the supplement”. This delegation rule also goes into the package and into its evaluation.
Recursion would always use the same work contract.
Each session would receive a Task object with:

The child can respond with a result, ask for information or propose further subtasks. The parent and the child use the same protocol, and that is what makes the system recursive.
Before starting new work, the engine tries, in order:
1. Retrieving an already verified result, if inputs and conditions match.
2. Applying a compatible active procedure.
3. Adapting an existing procedure, creating a candidate version.
4. Starting exploration and possible delegations.
Semantic similarity helps find candidates. Actual reuse also requires compatibility of data, criteria and versions.
When it proposes a delegation, the agent must explain which uncertainty it wants to resolve and how the answer will affect the parent’s work. The software then checks:
- Remaining budget and depth limit.
- Whether an equivalent task is already open.
- Circular dependencies.
- Clarity of the expected output.
- Available permissions and resources.
As an initial configuration I would try a maximum depth of 2 and 3 concurrently active sessions, with an overall limit on attempts. These are parameters to be measured, not properties of the paradigm.
The budget must belong to the whole tree. A child receives a share of the parent’s budget; creating more of them does not generate new resources. I would also keep a share reserved for verification and the final synthesis. The precision of the spending limit depends on the granularity with which the backend reports consumption; timeouts and number of runs can be controlled directly.
Child–parent communication would be persistent and structured.
A request for clarification would include:
{
  "type": "needs_context",
  "question": "Does the protocol require randomised or analysed participants?",
  "reason": "The paper reports both values",
  "affected_output": "participant_count",
  "evidence_refs": ["evidence_091"]
}
The parent looks for the answer in the project’s knowledge. If it finds it, it sends the reference; if it is missing, it can ask the researcher. Meanwhile the child waits and other work can proceed.
A waiting session does not occupy an execution slot. This avoids a practical problem: all the slots taken up by parents waiting for children that are unable to start.
The child’s result is verified before integration. The parent keeps the links to the original evidence: it should not receive only a summary that strips out doubts and conditions.
On the implementation side I would start from a small service, with a persistent queue and an adapter for Codex.
The service could be written in TypeScript and have these components:
Component	Responsibility
Scheduler	Starting, waiting, resuming, timeouts, budgets and cancellations
Codex adapter	Sessions, events, structured results and interruption
Execution archive	Inputs, outputs, actual code, events and consumption
Procedure registry	Versions, scopes, dependencies and activation status
Evaluator	Deterministic checks and content verification
Promotion process	Candidate creation, evaluations and registry update


The Codex SDK lets you start and resume sessions. For more detailed control, the App Server exposes turn start, events and interruption. Output constrained by a JSON Schema is also available, which is useful for the protocol between agent and service. Structured outputs.
For the first prototype I would use separate sessions managed by the service. This makes contracts, budgets and workspaces explicit. Native delegation remains an option, but it should not be confused with isolation: in the Agents API subagents share the environment’s filesystem. Native delegation.
Each worker would have its own directory or worktree. The worktree separates the changes; sandbox and permissions determine what it can actually touch. A central component integrates the results and updates the consolidated knowledge.
The central loop, in pseudocode, would be:
async def advance(task):
    context = retrieve_relevant_knowledge(task)
    procedure = select_qualified_procedure(task, context)

    outcome = await agent.run_turn(
        session=task.session,
        context=context,
        procedure=procedure,
        output_schema=TASK_OUTCOME_SCHEMA,
    )

    persist_outcome(task, outcome)

    if outcome.kind == "delegate":
        children = validate_and_reserve_delegations(task, outcome)
        enqueue(children)
        mark_waiting(task)

    elif outcome.kind == "needs_context":
        persist_question(task, outcome)
        mark_waiting(task)

    elif outcome.kind == "completed":
        enqueue_validation(task, outcome)

    elif outcome.kind == "blocked":
        record_blocker_and_notify_parent(task, outcome)
Events and artefacts should also be recorded during execution, so that a crash leaves an incomplete but inspectable attempt. The result becomes accepted only after validation.
Each request would have a unique identifier to avoid duplicate delegations or duplicate integrations after a restart. Cancelling the parent propagates to its descendants. Retries are limited, and external effects require idempotent operations or a reconciliation before retrying.
I would use SQLite for the operational state of the queue; knowledge records and procedures would remain versioned in Git. They are distinct responsibilities. Each promotion would record the package commit, the evaluation report, the policy version and the previous version. The active registry would be updated in a single operation, without modifying the versions already used by executions in progress.
The two engines meet when a delegation solves a recurring problem.
In your example:
1. The parent encounters an ambiguous denominator.
2. A child finds a decisive distinction in the supplement.
3. The answer is verified and linked to the annotation.
4. Other episodes show that this check recurs.
5. The learning process proposes a specific procedure.
6. The procedure passes the evaluations and becomes available.
7. At the next occurrence the system applies it directly, falling back on exploration only when the conditions do not match.
The first version should demonstrate exactly this complete cycle on a single family of problems: an experience becomes a verified procedure, is reused by a new session and is suspended when it meets a relevant counterexample. From there you can extend the recursion, already having the tools to understand whether it produces useful knowledge.

- An interface for inspecting results, decisions, delegations and checks.
- A correction mechanism that identifies the consequences for dependencies.
- An export and import format with integrity and completeness checks.
- A handoff test to a new user.
The latter would be the decisive test: a person, in a clean environment and without your conversation, must be able to explain a randomly sampled annotation, re-run an analysis, change a criterion and complete a new case.
The system would be complete when it can also transfer the work that is still open, together with the reasons why it is open and the conditions needed to continue it.
