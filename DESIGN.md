# WhiteSnake: design decision record

This document records the decisions taken in the discussions of 15 and 16 October 2026 (the first in `docs/origin/discussion.txt`, the second in the planning session). Each entry gives the decision, the reason and the consequences. Later discussions are dated and marked as open where no design has been settled. It is the starting point for anyone who inherits the project: the purpose of WhiteSnake is precisely to make this kind of knowledge transferable, so these decisions will be imported as the first records of the store as soon as the format exists.

## A. Vision and principles

1. **Deliver a process, not software.** Knowledge, decisions, procedures and an agent that uses them. The project's acceptance criterion is the *handoff test*: a person in a clean environment, without the original conversation, must explain a sampled annotation, re-run an analysis, change a criterion and complete a new case.
2. **Existing harnesses, no coding agent built from scratch.** Claude Code and Codex are the engine. A custom harness (pi or opencode) only in a later phase, and only for controls the harnesses do not expose: exact context assembly, interception of every model call, token accounting per subtree, deterministic replay.
3. **A core independent of domain and harness.** Record format, validator, index, CLI. Thin adapters: a single skill, a single hook script, headless invocation. The domain vocabulary lives in the project's skill, not in the schema.
4. **LLM sublation.** Procedures are a perishable layer: the next model may cover the gaps by itself. Decisions, criteria, evidence and provenance are durable. Hence: record granularity fixed at the level of the decision; procedure granularity decided by the agent at runtime; disposable procedures; at every model change, check "is it still needed?" by re-running the regression cases with the model alone.
5. **Converge to deterministic for reproducibility and API stability, not to make up for capabilities that future models will have.** Resolution order for every request: verified cached result → active code → frozen prompt → relevant agent. KPI: the fraction of closed episodes whose resolution is not `agent`, i.e. the height of the agentic frontier in the tree.
6. **Build order driven by the handoff test.** First the uncertainties (does the agent really consult the store? what granularity is needed? is delegation needed?), then the machinery. Every failure of the test points to the missing piece.

## B. Knowledge model

7. **Two linked structures.** A *fractal episode tree* (execution and delegation) and a *shared knowledge graph* (a DAG). Knowledge is not forced into the tree: the same evidence supports decisions in different branches.
8. **The cell** is the node of the tree, identical at every scale: `id`, `question`, `caused_by` (the turn of the prompt), `resolution` (cached | code | frozen_prompt | agent), `uses`, `produces`, `children` (local, or remote as `{store, id}`), `outcome` (success | failure | abstained | corrected), `input_hash`. A child store on a server is a cell with remote children: the parent sees the outcome and the references, not the internals.
9. **Node types:** `question`; `decision` in Toulmin form (claim, data, warrant, backing, qualifier, rebuttal) with a `kind` (annotation | criterion | choice) and a fragility label (mechanical | interpretive | analogical | absence); `evidence`, split into the *record* (verbatim excerpt, exact locator, hash) and the `artifact` (file with hash, portable and retrievable); `procedure` (resolution code | frozen_prompt | skill, entrypoint, uses, applicability, abstention, regression cases, source episodes, `qualified_on {harness, model}`, state provisional | trusted | suspended | retired with an append-only `history`); `episode`; `session` and `turn` from the native logs; `template` (compact node). **A criterion is a decision with `kind: criterion`**: annotations cite it as their warrant.
10. **The output database is derived.** Every cell of the database is generated by a decision of `kind: annotation` (unit, field, value); `whitesnake export-output` rebuilds CSV or SQLite from the decisions; `why <unit>/<field>` resolves to the decision. No binary file is a source of truth.
11. **Typed edges, written at decision time, never inferred from text**, with a single canonical direction per type: `data/backing/rebuttal` (decision → evidence), `warrant` (decision → criterion), `depends_on` (dependent → dependency), `produced_by` (node → episode), `uses` (episode → procedure/decision), `supersedes`, `answers`, `caused_by` (node → turn). The index derives the inverse views (`affected`, `supports`). Invalidation is correct only if the edges are. For decisions, the declared fields `warrant`, `backing` and `depends_on` are authoritative: if a criterion changes, a decision reached only through the episode that produced it is marked only if it declares nothing or declares that criterion; missing or inconsistent declarations are reported as warnings (`W_COARSE_EPISODE`, `W_UNCITED_CRITERION`), not as errors. The graph is a DAG and the validator enforces it: a cycle along `depends_on`, `warrant`, `backing` or `supersedes` between decisions, `uses` between procedures, or `parent` or `children` between episodes is rejected at write time and reported as `E_CYCLE`.
12. **Stable identifiers.** Authored nodes: type prefix + random suffix, never sequential (two parents working in parallel must not collide). Sessions and turns: derived deterministically from the native fields, so re-ingestion is idempotent.
13. **Toulmin at the meta level too.** Promoting a procedure is a decision with the same record: claim "P is adequate for T", data the accepted episodes, backing the acceptances seen, rebuttal the known failure cases. If B uses the output of A, B cites the version of A as backing: when A changes, B goes back to provisional. A demotion is a materialised rebuttal.
14. **Walton's critical questions on a trigger, not always.** They are activated when a precedent is missing, when confidence is low, or when a procedure and the free agent diverge. Relevant schemes: from sign, from precedent, from the author's opinion, from absence (to be marked as weak). The taxonomy of reasoning types is only a fragility label. **RPL is not built.** The 2026-10-20 extension to methodological review is described in [section I](#i-critical-review-in-the-shared-skill).
15. **Fill and flag.** An interpretive gap is filled with a provisional decision marked "proposed", without blocking. The child has a declared mandate (`whitesnake.yaml`) to tell a gap from something out of scope.

## C. Promotion, demotion, sublation

16. **State transitions are CLI rules computed from recorded events, not judgements of the agent.** The agent records events (`episode close`, `correct`, `shown`, `case add`); the CLI derives the state and caches it in the frontmatter, and the validator checks that the cache and the derivation agree. Creation → provisional; N shown uses without a correction → trusted; a correction → suspended, with needs_review propagated along `depends_on` and `warrant`; run in every episode of a type → hook candidate. **The researcher never touches the state.** `shown` requires the turn it happened in, so every shown use is a persisted event; the validator checks that a procedure's shown uses never exceed the shown decisions produced with it (`E_COUNTER_MISMATCH`).
17. **Silence counts as acceptance only for results that were actually shown.** "Shown" is recorded in two ways: the agent calls `shown` when it presents results (a rule of the skill), and the Stop hook scans the final message for identifiers. A shown result is accepted if the next turn of the session does not correct it, or if the session ends without a correction. The results of a headless child are not shown until the parent presents them. Provisional results are sampled.
18. **Promotion = collapsing a subtree** that is entirely deterministic into a composed procedure; the agent call moves up one level. Demotion = re-expansion. Sublation = collapse into nothing: the model does the thing directly, the procedure is retired, and its outputs remain valid.
19. **Four operations, two of which prune.** Retirement by sublation (the composition is archived); invalidation by error (transitive needs_review, nothing deleted); replacement (what is deterministic is recomputed, what is interpretive is flagged; the rules are in [section J](#j-rewriting-procedures)); discarding a line of work (a git branch). Failed attempts are compressed into negative examples.
20. **Frozen prompt** = prompt + model with a pinned version + output schema + fixed context, as a direct API call, with mandatory regression cases.
21. **Learning engine v1 = three queries on the index:** procedures used in every episode of a type; procedures whose output was corrected; requests resolved by `agent` with no applicable procedure.

## D. Delegation, topology, branching

22. **Parent and child are a boundary of store ownership**, not a decomposition of reasoning. Criteria and the knowledge version flow down; results, evidence and stable references flow up. The child exposes the "why" as its interface. Depth = the topology of the stores. **For now the boundary is simulated**: two directories, headless invocations.
23. **A two-layer CLI.** Deterministic primitives, and on top of them `ask`, which launches Claude Code or Codex headless on the store with an output schema and returns the answer plus identifiers. The child uses the same primitives. The write validator lives in the child.
24. **Branching per parent.** The parent's identity is the **parent store** (its id in `whitesnake.yaml`); every use of the child happens on the branch `parent/<store-id>` in a worktree; rebase on main when it is opened (conflict → exit with an error, no partial state); three merge policies: append-only evidence merges by itself, decisions and criteria require explicit reconciliation, CLI code enters main only if it passes the contract tests. **Semantic reconciliation is deferred.** User-level identity comes in a later phase.
25. **The child may modify itself as much as needed** on its own branch; a change to the skill or the CLI is recorded as a decision.
36. **Gaps are covered by the coding agent, and memory is imprinted in the pertinent store.** When a procedure is missing, the coding agent working in that store covers the gap, not a human and not a rigid fallback. The knowledge produced by covering a gap belongs to the store that owns the gap's domain: the child that provides the service, not the parent that calls it. The parent receives the result and stable references and records only the evidence of the exchange. If ownership is blurry, or delegation to the child is not possible, the memory still goes into the child and never into the parent: the CLI, used from inside one store towards another, works on the child's `parent/<caller-id>` branch, mirrors the caller's session and turn there so that provenance resolves locally, and attributes the records to the caller's agent. The child's main changes only through reconciliation.

## E. Observability and compaction

26. **Every record carries its turn of origin.** The UserPromptSubmit hook creates the `turn` node at the start of the turn and writes `.whitesnake/current-turn`, so `caused_by` is available during the session, not only after ingestion. A `timeline` command. A static HTML page generated from the index, with KPIs (procedures by state, promotions and demotions per session, fraction resolved without an agent). **Read-only**: corrections go through the agent.
27. **The native logs are the experience layer**, extracted by a parser, retroactively too. For headless children the authoritative transcript is the `--json` stdout captured in `.whitesnake/transcripts/`.
28. **The SQLite index holds nothing unique.** Everything that reports, KPIs and handoff need lives in the records; the index can always be rebuilt.
29. **Compaction = garbage collection.** Live roots: `active` decisions, provisional or trusted procedures, current output rows, open questions, the HEAD of every parent branch. Cold: a subtree whose episodes are all closed, from which no provisional, needs_review or open question is reachable, older than N sessions (default 5). Compact: `template` nodes with `compacted_from {count, commit, ids}`, a summary in the shape of the cell plus Toulmin, locators, negative examples. Sweep: from the working tree; git history keeps the raw files, so `gc --apply` requires git and commits the working tree before sweeping: the commit it records contains every raw record it replaces. Validator: every edge from an active node must resolve, otherwise the change is rejected. At handoff, the manifest states whether history is excluded.
37. **Writes are verified by result, not by command.** The PreToolUse hook refuses the hand edits of `knowledge/` it can recognise in a command line, but a text pattern can never be complete: a write from python, after a `cd`, through git or through a variable all look different. So the CLI keeps a journal of every file it writes or removes under `knowledge/` (path and content hash, in `.whitesnake/writes.jsonl`), and at every Stop the hook compares the tree with the snapshot taken at the previous check: a changed file without a receipt for exactly its current content was written outside the CLI. It is reported to the researcher, logged in `hooks.log`, and counted by the live tests instead of classifying commands. Our own git operations that rewrite `knowledge/` (branch rebase and merge) move the baseline with them. The command guard stays as a nudge.
38. **Sources are verified by content.** An artifact is registered with its sha256 and the validator compares the file with it (`E_ARTIFACT_HASH`), trusting a size and modification-time cache in the working store and re-reading every file at `check`. A source that changed since registration makes the store invalid, because every locator into it is suspect; a new version is registered as a new artifact. The resolution ladder reuses only `active` decisions: one under review after a correction is answered with `review` and must be redone and superseded.

## F. Stack and tools

30. **A core we build ourselves:** format, validator, indexer, CLI, log parsers, HTML renderer. The big parts are not ours: the agent loop (the harness), PDF parsing (procedures written by the agent, usually in Python), model calls (the API).
31. **Strict TypeScript on Node**: `node:sqlite`, `node:test`, `zod`, no native dependencies; precedent search with our own inverted index, because `node:sqlite` does not include FTS5; `better-sqlite3` only as a fallback. A single executable for handoff (Node SEA) or, failing that, `npm install -g`.
32. **Store = text files in git + a rebuildable SQLite index.** An embedded graph database only as a possible replacement for the index, never as the source of truth.
33. **External tools:** from graphify we copy the "query before reading" hook pattern; optional use in phase 2, only on the corpus folder, never on the store. From codegraph, the tree-sitter approach to derive dependencies between procedures, in phase 2 and inside our indexer. codemem is not used. Deciduous is the inspiration for the shape of the records.
34. **Out of scope for now:** scheduler and queue, OpenTelemetry, RO-Crate, graph database, network transport, semantic reconciliation, custom agent, user identity.

## G. Layout

35. **Two repositories.** This is the *tool* repository (CLI, skill, hooks, documentation, tests, the toy store in `examples/`). Every *project* is a separate store with its own git repository, created by `whitesnake init`. The source files of the discussion are in `docs/origin/`.

## H. Open discussion: generalization and cost at scale

**2026-10-20 — Critical unresolved design question.** Annotation at the scale of a database such as CELLxGENE requires the agent to amortize reasoning across many records. Preferring deterministic code does not by itself achieve this: code can be specific to each case, and a reusable procedure can still require model intervention for every invocation. Existing toy tests do not establish affordable operation at this scale.

**Working hypothesis.** Explicitly ask the agent to discover reusable rules and automate their application. Profile the corpus with code, reuse structured information, identify families of cases, develop rules from informative examples, validate on separate cases, then execute batches and group exceptions for further reasoning. Preserve provenance for every decision and require evidence for any result propagated across a group. The skill contains this as experimental operating guidance; its effectiveness remains to be tested.

**Current implementation boundary.** `procedure propose` parameterizes recorded command executions; the agent must still determine applicability and whether the rule generalizes. `collapse` writes a composed skill in `STEPS.md`, rather than an autonomous batch executable. The KPI counts declared episode resolutions and does not account for actual model calls, tokens or total spending. The promotion threshold based on shown uses does not establish population-level accuracy. Budget instructions and individual harness limits do not establish an aggregate budget across retries and delegated work.

Questions to resolve:

- **Instruction or enforcement?** How much improvement comes from the generalization guidance alone? Which parts need executable support: applicability checks, batch execution, exception grouping, metering and aggregate budget enforcement?
- **Quality and scope?** How should representative and independent validation cases be selected? Which accuracy, coverage and abstention criteria justify applying a procedure broadly? Check across studies or datasets when repeated observations would otherwise make validation misleading.
- **Economic stopping point?** When does expected reuse justify the cost of discovering, testing and maintaining a broader rule? The proposed objective is total cost per correct result subject to quality and coverage requirements, including the cost of recording provenance.
- **Sublation?** Model capability establishes that replacement is possible; it does not establish that replacement is cheaper. Retaining a deterministic procedure may be preferable for repeated execution even after the model passes its regression cases. The current `recheck` tests capability, not economic benefit.

**Proposed evaluation, not yet run.** Compare the existing procedure-reuse workflow with the experimental guidance on the same bounded corpus, task and budget, using independent validation cases and repeated runs. Measure actual calls, tokens, total cost and elapsed time—including orchestration, retries, delegation, rule development, validation and recording—alongside automatic coverage, observed errors, unresolved cases and provenance completeness. Increase corpus size to test whether reuse reduces cost per correct result while quality holds. Use the findings to decide which runtime controls to build; do not infer savings from a higher fraction of episodes labelled `code`.

## I. Critical review in the shared skill

**2026-10-20 — Implemented as agent guidance; effectiveness remains open.** Extend the existing Walton-inspired questions to task definition, generalization, cost and completion. Trigger the relevant review at consequential decisions, reuse it within its recorded scope and reopen it when assumptions or evidence change. Ordinary execution within a reviewed scope keeps its normal checks.

The agent first answers from the conversation, store and bounded investigations. It owns delegated implementation choices and tests methodological choices against the user's criteria. User input is needed for an unresolved choice that changes meaning, goals, acceptable error, coverage or resources; previous answers are reused. Only dependent work waits for that answer. Filling a gap provisionally does not authorize applying an unaccepted criterion across a population.

The [shared skill](skill/whitesnake/SKILL.md#critical-review) routes to the [critical questions](skill/whitesnake/references/walton-checklist.md). Reviews use existing evidence, decision, question and episode records, with explicit dependency links and concise findings. No new schema, CLI command or automatic approval stage is introduced. Store validation and procedure promotion retain their existing meaning; neither proves semantic correctness or population accuracy.

Evaluate this guidance alongside the experiment in section H: measure errors avoided, reuse, cost and user interruptions. Confirm that existing criteria prevent repeated questions, technical choices remain delegated, unsupported generalization stays bounded, and completion claims cite relevant checks. Hard budget enforcement remains a separate runtime question.

## J. Rewriting procedures

**2026-10-30 — Decided and implemented.** The discussion started from a gap: an agent that decides to rewrite a procedure instead of reusing it had no rule for whether the rewrite is better, no record of why it was made, and nothing stopped it from editing the old code in place. The 15 October conversation had already asked for versioned procedures, comparison on separate cases, shadow mode and a policy fixed before the evaluation; only decisions 13 and 19 carried a trace of it.

39. **Code that produced a result never changes.** A procedure record carries `code_hash`, the sha256 of its entrypoint at registration, filled by `add`, `propose` and `collapse`; the validator compares the file with it (`E_PROCEDURE_HASH`), as it does for artifacts (decision 38). An edit in place would leave every past execution pointing at code that is no longer there. `procedure rehash` re-registers the hash only while no episode, decision or procedure has used it. A change is a new procedure.
40. **A rewrite names what it replaces and why, in a checkable form.** `supersedes` lists the replaced procedures; a `justification` is required with it (`E_UNJUSTIFIED_SUPERSESSION`): a `kind` from a closed list (correctness, performance, scope, platform), the record ids that prove it, and free text for the reader. Prose alone is not a justification, by the same rule that forbids provenance in prose. `supersedes` joins `uses` in the acyclicity check.
41. **"Better" is dominance on the recorded battery, not a score.** Every procedure carries a battery nobody wrote by hand: its regression cases, plus one case per distinct input it was run on, labelled by what the researcher did with the value (accepted, corrected with or without the right value, never confirmed, or the procedure failed). `procedure compare <old> <new>` replays the battery with the new code and judges each case against the record: same, fixed, regression, still_wrong, changed_unverified, agree, diverge, gained, stale. The new procedure dominates when no case regresses, no case diverges without an accepted value, and at least one improvement is shown: a fixed case; new cases covered, for a scope rewrite; a lower median latency on the same host and inputs, for a performance rewrite; running where the old one does not, for a platform rewrite. A rewrite that fixes one case and breaks another is different, not better: the diverging cases go to the researcher. The report is recorded as execution evidence with the hashes of both entrypoints.
42. **Coexistence is shadow mode, with the mechanics already in place.** The new procedure starts provisional. The agent runs both on new inputs, lists both in the episode's `uses` and shows one value: an agreement earns both a shown use (decision 16), a disagreement keeps the trusted value, records the other output as rebuttal evidence and raises a question. `resolve` names such pairs and says what to do with them.
43. **The replacement is a CLI rule, and a decision.** `procedure supersede <new>` requires the new procedure to be trusted, to dominate on a fresh comparison, and to clear every applicable threshold criterion. It then records a `choice` decision (claim "new supersedes old", data the comparison evidence, warrant the threshold criteria applied, backing the justification's evidence, `depends_on` both procedures) and moves the old procedure to the new state `superseded`: out of the resolution ladder, no shown uses, corrections counted but no transition, past outputs standing. The validator requires a successor for every superseded procedure (`E_SUPERSEDED_NO_SUCCESSOR`). Reinstatement stays possible if the successor fails.
44. **Discontinuation is compaction, never deletion.** A procedure's record cannot leave the store while any value points at it, which in annotation means never. `gc` archives the code of cold superseded and retired procedures instead: the record gets `code_archived` with the commit that holds the code and the paths removed (the entrypoint, or its directory when no other procedure lives there); `check` and `resolve` already ignore procedures that are not live. There is no clean command: collapse, not prune (decision 29).
45. **Measurements are derived; thresholds are decided.** `procedure scorecard` computes from the records: episodes and sessions of use, outputs produced, shown and corrected, the observed error rate (corrections over observed outputs, a lower bound), regression check failures from the history, latency per platform and host, and the distinct code versions seen in executions. Executions now record a short hash of the host, since the platform label cannot tell two machines apart. A bar on these numbers is a `criterion` decision with a `threshold` (`metric`, `max`, `min_shown`, `procedures`), evaluated by the scorecard as met, violated, insufficient or unavailable, required by `supersede`, and reopened through `affected` like any criterion. With no threshold declared, dominance is the rule and the faster procedure wins at equal results.

**Limits stated.** The battery is as good as what was shown: silence can be a distracted review, so the observed error rate bounds the true rate from below (section H). Comparison replays code procedures only; frozen prompts and skills need a sampled comparison the agent records as evidence. Latency is noisy and only comparable on the same host and inputs. `qualified_on` is still never written by the CLI. Whether agents follow the shadow-mode discipline is a matter for the live tests, not yet run on this feature.

## K. Network of nodes: foundations

**2026-11-06 — Decided; implemented one decision per commit.** The plan for a network of nodes (stores hosted as nodes, persistent sandboxes per parent and project inside the child, acceptances and corrections returned from the parent to the sandbox) rests on three local foundations that the simulated boundary of decision 22 already lacks: procedure state derived from events rather than cached counters, one active annotation per cell with idempotent corrections, and typed references across stores. Each decision below enters this record with the commit that implements it.

46. **Continuous integration is the gate before a second host.** Every push runs the deterministic suite on Ubuntu and macOS with Node 22.13 and 24 (`.github/workflows/test.yml`), followed by `gate` against `contract.json`. The suite uses the stub harness only. The workflow injects a git identity through the environment, because the CLI's own commits (branch open and merge, the Stop hook, `gc`, `init`) pass none. Until now the code had run on one macOS machine; nothing about a second node is tried before the four combinations are green.
47. **A procedure's state is a replay of recorded events; the record caches it.** Decision 16 said the CLI derives states from events and caches them; in practice `shown` and `correct` incremented counters and appended history inside the procedure file, so two branches that used the same procedure fought over a line, and their numbers did not add up. Now the events live on the decisions: a decision shown to the researcher carries the turn and the moment (`shown_at`), a correction is an identified entry (`corrections`: turn, moment, reason, event id, actor), and every explicit transition (reinstate, retire, supersede, the suspension a failed `check` applies) is a `choice` decision that names the procedure in `depends_on`, carries `transition` and cites its evidence. The derivation (`src/lifecycle/derive.ts`) replays a procedure's events in time order, creation first, ties broken by kind (shown, corrected, explicit) and then by source: provisional → trusted at the threshold without a counting correction; provisional or trusted → suspended on a counting correction or an explicit suspension; suspended → provisional on reinstate, with counters reset; provisional or trusted → retired; provisional, trusted or suspended → superseded; superseded or retired → provisional only through a reinstate with evidence. Anything else is reported (`W_TRANSITION_IGNORED`) and not applied. A correction counts for the state only when its actor owns the branch context: `human:researcher` on main, `human:researcher@<parent-id>` on `parent/<parent-id>`; the default actor of `correct` is that owner, so a correction counts where it is made. `state`, `counters` and `history` stay in the file for the reader, as a cache: the validator replays the events and rejects a cache that disagrees (`E_STATE_MISMATCH`, `E_COUNTER_MISMATCH`, `E_HISTORY_MISMATCH`), and `procedure recompute` rewrites it. A bare turn id in `shown_at` is an older record whose moment is unknown; its turn's timestamp stands in.
48. **Caches are derived again where histories meet.** `branch merge` merges without committing, treats a conflict confined to the cached fields of a procedure as no conflict (either side is taken, the cache is derived from the union of events), recomputes every procedure, validates the merged tree and only then commits; a real conflict, or an invalid result, aborts and leaves main untouched. `branch open` does the same through a rebase and commits the recomputed cache on the branch. The toy store's caches are derived the same way by `make-toy`, which is how its literal counter was found to be one short.
